从最初的一个 HTML 单页想法，到最终部署在 Cloudflare 边缘节点上的 Next.js 全栈应用，整个项目经历了 原型 → 重建 → 部署 → 云同步 → 修 Bug → 域名绑定 六个阶段。最终产品包含 7 大生活管理模块，支持 localStorage 本地持久化 + Cloudflare KV 云端同步双层架构，自定义域名 cclixx.fun 已上线。

二、开发时间线

阶段 1：HTML 原型
用单个 HTML 文件快速实现 7 大模块（记账、习惯、健身、日程、购物、书影音、今日概览），验证产品概念和交互逻辑。6 个数据库对应 6 个 localStorage key。
阶段 2：Next.js 重建
迁移到 Next.js 14 App Router + TypeScript + Tailwind CSS。创建了 19 个源文件：7 个模块组件、6 个自定义图表组件（BarChart / DonutChart / HeatGrid / LineChart / MiniBarChart）、4 个 lib 工具库、1 个类型定义文件。采用静态导出模式 output: 'export'。
阶段 3：Cloudflare 部署
配置 wrangler.toml，创建 KV namespace（binding: DATA_STORE），编写两个 Pages Functions（/api/save 和 /api/load）作为无服务器后端。注意：Functions 文件必须是 .js 而非 .ts。
阶段 4：云同步实现
前端 cloudStorage.ts 通过 fetch('/api/save') 和 fetch('/api/load') 调用边缘函数。实现了 useCloudSync hook 管理页面级加载/自动保存生命周期，debouncedSaveToCloud 做防抖保存。
阶段 5：Bug 修复（3 轮）
第 1 轮（commit 7cf02e9）：云加载覆盖本地新数据 — 按 id 合并数组。
第 2 轮（commit e28f62a）：useLocalStorage 反馈循环 — 添加 serializedRef 机制。
第 3 轮（commit 251f1d2）：合并策略升级为时间戳比较，取 updatedAt 较新版本。
阶段 6：域名绑定
将默认 *.pages.dev 域名更换为自定义域名 cclixx.fun，通过 Cloudflare Dashboard → Workers & Pages → Custom domains 完成。源代码使用相对路径，无需任何修改。

3.3 关键设计决策

静态导出而非 SSR： 使用 output: 'export' 生成纯静态 HTML，部署到 Cloudflare Pages 后由 CDN 直接分发。后端能力通过 Pages Functions（边缘函数）实现，不依赖 Next.js 服务端运行时。这意味着 API 路由不在 app/api/ 下，而在 functions/api/ 下，由 Cloudflare 运行时接管。

API Secret 硬编码而非环境变量： 原计划使用 NEXT_PUBLIC_API_SECRET 环境变量，但 Cloudflare Pages token 权限不足无法设置环境变量。由于 NEXT_PUBLIC_ 前缀变量在构建时内联到 JS bundle 中，与硬编码安全性等价，最终直接在 cloudStorage.ts 中硬编码 API_SECRET，Functions 端通过 env.API_SECRET（Cloudflare 环境变量）校验。

6 个自定义图表而非引入图表库： 没有使用 Chart.js 或 Recharts，而是用纯 SVG 实现了 BarChart、DonutChart、HeatGrid、LineChart、MiniBarChart 五种图表。好处是零依赖、bundle 更小、完全可控的样式，与纸墨+清新绿设计语言一致。

四、数据持久化双层设计

这是项目中最核心、也是花最多时间调试的架构。数据存储分为两层：

4.1 第一层：localStorage 本地持久化

核心 hook：useLocalStorage<T>(key, initialValue)

  • SSR 安全： 初始值在客户端 mount 后从 localStorage 读取，避免 hydration 不匹配
  • 跨组件同步： 监听自定义事件 local-storage-sync + 原生 storage 事件（跨标签页）
  • 防反馈循环： serializedRef 跟踪最后写入的 JSON 字符串，写入和同步监听都先比较序列化值
// 防反馈循环核心逻辑
const serializedRef = useRef<string | null>(null)

// 写入 effect：仅在序列化值变化时写入
useEffect(() => {
  const serialized = JSON.stringify(value)
  if (serializedRef.current === serialized) return  // 防止自触发
  serializedRef.current = serialized
  localStorage.setItem(key, serialized)
  window.dispatchEvent(new CustomEvent('local-storage-sync', ...))
}, [key, value, loaded])

// 同步监听：仅在传入 JSON 不同时更新
function onSync(e: Event) {
  const raw = localStorage.getItem(key)
  if (serializedRef.current === raw) return  // 防止 setValue→write→onSync 循环
  serializedRef.current = raw
  setValue(JSON.parse(raw))
}

4.2 第二层：Cloudflare KV 云端同步

核心 hook：useCloudSync() + 工具库 cloudStorage.ts

  • 页面级加载： 应用初始化时 loadAllFromCloud() 加载 9 个 key 的数据
  • 自动保存： 监听 local-storage-sync 事件，对变更的 key 做 debouncedSaveToCloud（2 秒防抖）
  • 避免循环： 跳过 source === 'cloud-load' 的事件，防止 save→load→save 循环
  • 时间戳合并： 云端与本地数据按 id 合并，冲突时取 updatedAt（或 createdAt）较新版本

五、关键 Bug 与解决方案

Bug 1：云加载覆盖本地新数据 竞态条件

现象： 用户在页面打开后添加了一条日程，此时云端数据加载完成，直接覆盖 localStorage，用户新添加的日程消失了。

根因： loadAllFromCloud() 原先直接 localStorage.setItem(key, JSON.stringify(data))，用云端数据替换本地数据，没有考虑加载期间用户可能已有新写入。

解决（3 轮迭代）：

  1. v1（commit 7cf02e9）：数组按 id 合并 — 云端有但本地没有的加入，本地有但云端没有的保留
  2. v2（commit 251f1d2）：时间戳冲突解决 — 对相同 id 的项目，比较 updatedAt（fallback createdAt），取较新版本
  3. v3：事件精准派发 — 只对实际收到云端数据的 key 派发 local-storage-sync 事件（原先对全部 9 个 key 派发，导致不必要的覆盖）
// 时间戳合并核心逻辑
const getTimestamp = (item) => item.updatedAt ?? item.createdAt ?? 0

const mergedMap = new Map()
// 先放入本地数据
for (const item of existing) mergedMap.set(item.id, item)
// 再合并云端数据，冲突取较新版本
for (const item of cloudData) {
  const local = mergedMap.get(item.id)
  if (!local) {
    mergedMap.set(item.id, item)  // 云端独有
  } else if (getTimestamp(item) > getTimestamp(local)) {
    mergedMap.set(item.id, item)  // 云端更新
  }
}

Bug 2：useLocalStorage 反馈循环 无限循环

现象： 云同步加载后，页面状态反复更新，浏览器卡死。

根因： setValue → 写入 effect 派发事件 → onSync 监听器 setValue → 再写入 → 再派发… 因为 JSON.parse 总是创建新引用，=== 比较对象不等，导致无限循环。

解决（commit e28f62a）：引入 serializedRef，存储最后写入/读取的 JSON 字符串。写入 effect 和 onSync 监听器都先比较序列化值，相同则跳过。

Bug 3：Pages Functions 文件后缀 部署

现象： 部署后 API 返回 Invalid module 错误。

根因： Cloudflare Pages Functions 只识别 .js 文件，不识别 .ts。

解决： 将 functions/api/save.ts 和 functions/api/load.ts 重命名为 .js，确保语法为 ES Module 格式（export async function onRequestPost）。

Bug 4：save→load→save 循环 逻辑循环

现象： 云加载触发 local-storage-sync 事件 → 自动保存 effect 监听到 → 又保存到云端 → 又加载…

解决： 云加载派发事件时带上 source: 'cloud-load' 标记，自动保存 effect 跳过带此标记的事件。

// 自动保存 effect
useEffect(() => {
  function onSync(e: Event) {
    const ce = e as CustomEvent
    if (ce.detail?.key !== key) return
    // 跳过云加载事件，避免 save→load→save 循环
    if (ce.detail?.source === 'cloud-load') return
    debouncedSaveToCloud(key, data)
  }
  window.addEventListener('local-storage-sync', onSync)
}, [])

六、经验教训总结

✅ 做得好的

  • 渐进式开发： 先 HTML 原型验证概念，再 Next.js 重建，降低了风险
  • 类型先行： types/index.ts 统一定义所有数据结构，所有模块共享
  • 零依赖图表： 用纯 SVG 实现图表，bundle 更小，样式完全可控
  • 双层持久化： localStorage 即时响应 + KV 云端备份，离线可用
  • 防抖保存： 2 秒防抖避免频繁 API 调用
  • 相对路径 API： fetch('/api/save') 使用相对路径，换域名零修改

⚠️ 可改进的

  • Secret 暴露： API_SECRET 硬编码在前端 JS 中，任何人可查看。应改用 OAuth 或 Cloudflare Access
  • 无用户体系： 所有数据共用一个 KV namespace，无法区分多用户。应加 userId 前缀
  • 无离线检测： 没有检测网络状态，离线时 API 调用静默失败
  • KV 无过期： 删除的数据在 KV 中不会自动清理，需要手动管理
  • 无自动化测试： 没有 unit test 或 e2e test，依赖手动验证
  • 无错误上报： 用户遇到的错误不会通知开发者

最有价值的经验

这个项目最大的收获是状态同步的复杂性。一个看似简单的"本地存储 + 云同步"需求，涉及了竞态条件、反馈循环、数据合并策略三个层层递进的问题。每一个都是在前一个修复后才暴露出来的，需要逐步深入。最终的 serializedRef + 时间戳合并 + source 标记三重防线，是实战中摸爬滚打得来的，不是看文档能预见到的。

第二部分：新功能路线图

基于现有 7 大模块的架构和数据结构，以下是 12 项可加入的新功能建议，按优先级分为三档：

12 项新功能建议

1. 用户认证与多设备隔离

当前所有数据共用一个 KV namespace，无法区分用户。加入简单的用户系统（如邮箱+密码或 OAuth），每个用户的数据存储在 user:{userId}:ld_accounts 这样的 key 下。这是真正多设备同步的前提。

技术方案： Cloudflare Workers + D1（SQLite）存储用户信息，JWT token 认证。或者用 Cloudflare Access 零代码认证。

后端前端基础设施

2. PWA 离线支持 + 安装到桌面

添加 manifest.json 和 Service Worker，让应用可安装到手机/桌面。离线时所有操作正常工作（已有 localStorage），联网后自动同步到云端。配合"离线检测"功能，联网状态切换时给用户明确反馈。

技术方案： next-pwa 或手写 Service Worker + navigator.onLine 检测。

前端基础设施

3. 数据统计仪表盘（Dashboard）

在"今日概览"模块基础上，新增一个独立的数据分析页面，汇总跨模块的洞察：

  • 月度财务报告： 收支趋势折线图、分类支出饼图、同比环比
  • 健康趋势： 体重+体脂率双轴折线图、BMI 演进、习惯连续天数热力图
  • 时间分析： 日程完成率、高优先级任务占比、周/月任务量柱状图
  • 消费习惯： 购物清单总价趋势、已购/未购比例

技术方案： 复用现有 6 个图表组件，新建 components/modules/Dashboard.tsx。

前端

4. 日历视图（月历 + 周历）

为日程模块添加完整的月历/周历视图，将 ScheduleItem 按日期展示在格子中。支持拖拽调整日期、点击日期快速添加。同时叠加记账和健身记录，一个日历看到所有当天活动。

技术方案： 纯 CSS Grid 布局日历 + HTML5 Drag and Drop API，不引入全量日历库。

前端

5. 提醒通知系统

为日程和习惯添加提醒功能：

  • 每日固定时间提醒打卡习惯
  • 每周日推送本周回顾

技术方案： Notification API + Service Worker push（需后端定时触发）。简单版可用 setTimeout + Notification.requestPermission()。
